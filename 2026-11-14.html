허용 목록은 글자를 보고, 샌드박스는 실행을 본다

오늘 조사한 것 중 지금 당신에게 학습 가치가 있다고 판단한 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

하네스 설계 · 오늘의 핵심 공식 릴리스 노트 · 공식 문서 빨리 바뀜

Claude Code 2.1.325, 허용 규칙이 이름과 다른 프로그램을 통과시키던 구멍을 막았다

WHAT

Claude Code 2.1.325가 11월 13일 나왔다. 권한 검사와 관련된 수정이 여러 줄 들어 있다. 그중 핵심은 아래 다섯 가지다.

  • Bash 허용 규칙이 규칙에 적힌 것과 다른 프로그램을 실행할 수 있던 경우를 고쳤다.
  • 일부 복합 명령이 묻지 않고 실행되던 빈틈을 고쳤다. 이제는 묻는다.
  • 재시작 뒤에 도착한 승인에 거부 규칙이 적용되지 않던 문제를 고쳤다.
  • 샌드박스 안에서 도는 Bash 명령도 기본적으로 일반 권한 절차를 거치게 바꿨다.
  • 작업 트리의 설정과 훅을 샌드박스가 완전히 보호하지 못하던 경우를 고쳤다.

릴리스 노트는 어떤 입력으로 뚫렸는지 밝히지 않는다. 그래서 구체적인 공격 형태는 이 글에서 추측하지 않는다.

WHY

이번 수정은 버그 몇 개를 메운 것이다. 그런데 그 바탕에 있는 한계는 공식 문서에 이미 적혀 있다. 문서의 문장은 이렇다.

"Bash 규칙은 Claude가 쓴 명령 텍스트에 맞춰진다. 같은 프로그램을 다른 형태로 부르면 맞지 않는다. 그래서 프로그램 둘레의 보안 경계가 아니다."

문서는 예시 표까지 싣고 있다.

  • Bash(rm *) 규칙은 rm -rf build/를 잡는다. 하지만 /bin/rm -rf build/나 bash -c 'rm -rf build/'는 못 잡는다.
  • Bash(git push *) 규칙은 git -C . push origin main을 못 잡는다.

문서의 결론도 분명하다. 명령 텍스트와 무관하게 막아야 한다면 샌드박스를 쓰라고 한다. 샌드박스는 실제 프로세스의 파일·네트워크 접근을 운영체제 수준에서 검사한다.

FOR YOU

이 구조는 당신이 이미 한 번 판정한 적이 있다. 9월 재평가에서 당신은 "위험 키워드를 걸러내는 함수"를 기각했다. 우회 경로가 너무 다양하고, 실행되는 쿼리 자체가 바뀔 위험을 못 벗어난다는 이유였다.

Bash 허용 규칙이 바로 그 키워드 필터다. 규칙이 놓인 위치는 문제가 없다. 모델이 고칠 수 없는 자리에 있고, 모든 명령이 그 앞을 지나간다.

새는 곳은 위치가 아니라 규칙의 커버리지다. 당신이 SQL 문항에서 따로 떼어 다룬 바로 그 축이다.

그러면 prepared statement에 해당하는 것은 무엇일까. 샌드박스다. 둘은 같은 방식으로 문제를 피한다.

  • prepared statement는 입력 문자열을 해석하지 않고 쿼리 구조를 미리 고정한다.
  • 샌드박스는 명령 문자열을 해석하지 않고 실제로 열리는 파일과 연결을 검사한다.
  • 둘 다 "입력이 어떤 모양인가"를 판정 기준에서 빼 버린다.

당신의 야간 브리프 하네스로 가져가 보자. 허용 목록에 Bash(python *)와 Bash(git *)가 있다.

python -c "..." 한 줄이면 파이썬이 할 수 있는 모든 일이 규칙 안에 들어온다. 이 목록이 허용한 것은 영수증 스크립트가 아니라 "python으로 시작하는 글자"다.

규칙을 Bash(python tools/nightly_state.py *)처럼 좁히면 나아지긴 한다. 하지만 그것도 글자 비교 안에서의 개선이다. 하네스가 절대 못 건드리게 할 파일이 있다면 그 보호는 OS 계정 권한이나 샌드박스에 둬야 한다.

AX 강의에서도 같은 질문이 나온다. "허용 목록 잘 만들면 안전하죠?"

허용 목록은 자주 쓰는 형태를 덜 묻게 하는 편의 장치다. 반드시 막아야 하는 일은 실행을 보는 층에 맡긴다.

LEARN

버전 소식 자체는 알아두기만 하면 된다. 업데이트하고 넘어가도 된다.

오래 가는 것은 "글자를 보는 검사"와 "실행을 보는 검사"의 구분이다. 셸 명령, SQL, 프롬프트 필터 모두 같은 틀로 읽힌다.

더 보고 싶다면 공식 권한 문서의 "What a Bash rule doesn't match" 표 세 줄을 읽어 보자. 그다음 샌드박스 문서에서 파일·네트워크 제한을 어디에 적는지 보면 된다.

당장 할 일은 하나다. 야간 하네스 허용 목록에서 python과 git 규칙이 실제로 무엇을 허용하는지 한 번 따져 본다.

3줄 요약

  1. Claude Code 2.1.325는 Bash 허용 규칙이 이름과 다른 프로그램을 실행하거나 일부 복합 명령이 확인 없이 실행되던 문제를 고쳤다.
  2. 샌드박스 Bash 명령은 기본적으로 일반 권한 절차를 따르게 바뀌었고, 작업 트리의 설정·훅 보호와 압축 응답 해석의 보안 문제도 수정됐다.
  3. 공식 문서에 따르면 Bash 규칙은 명령 글자에만 맞춰져 /bin/rm이나 bash -c 같은 다른 호출 형태는 막지 못하므로, 파일·네트워크 제한에는 샌드박스를 써야 한다.

왜 지금 이걸 다루는지

방금 본 릴리스 노트에는 "고쳤다"는 문장이 여럿 있다. 그런데 당신 쪽에서 그게 사실인지 확인할 방법은 아직 없다. 다음 업데이트에서 다시 깨져도 알아챌 장치도 없다.

이 빈자리를 채우는 것이 회귀 시험이다. 업데이트마다 같은 시험 세트를 다시 돌려 이전 결과와 비교한다. 핵심은 시험할 대상을 두 구간으로 나누는 데 있다.

두 구간

같은 하네스 안에도 성질이 다른 두 부분이 있다.

  • 결정론 구간은 같은 입력이면 항상 같은 결과가 나온다. 권한 검사기가 여기에 속한다. 같은 명령 글자를 넣으면 늘 같은 판정이 나온다.
  • 확률 구간은 같은 입력에도 결과가 달라진다. 모델이 우회 형태의 명령을 시도하느냐가 여기에 속한다.

두 구간은 시험하는 방법이 다르다. 결정론 구간은 한 번 돌리고 정확히 일치하는지 본다. 확률 구간은 여러 번 돌리고 비율을 본다.

결정론 구간의 시험 세트

권한 검사기용 시험 세트는 세 묶음이면 된다. 각 명령 옆에 기대 판정을 먼저 적어 둔다.

  • 반드시 통과해야 하는 정상 명령. 예를 들어 영수증 기록 명령이다.
  • 반드시 묻거나 막아야 하는 우회 형태. 절대경로, bash -c, python -c가 여기 들어간다.
  • 판정이 애매한 경계 사례. 결과를 보고 기대값을 정한 뒤 고정한다.

업데이트가 오면 이 세트를 돌리고 이전 결과와 비교한다. 바뀐 줄이 있으면 그게 사람이 볼 부분이다.

두 구간을 섞으면 생기는 실패

  • 결정론 구간을 확률처럼 다루면 "가끔 뚫린다"를 운으로 넘긴다. 결정론 구간에서 한 번 뚫렸다면 그 입력은 매번 뚫린다.
  • 확률 구간을 결정론처럼 다루면 한 번 통과를 "고쳐졌다"로 읽는다.

확률 구간에는 함정이 하나 더 있다. 20번 돌려 우회 시도가 0번이어도 그건 "없다"가 아니라 "드물다"다. 그래서 반드시 막아야 하는 일은 결정론 구간, 곧 샌드박스나 OS 권한에 둔다. 첫 번째 항목의 결론과 같은 이야기다.

FOR YOU

당신은 이미 결정론 구간 시험을 갖고 있다. 이 저장소의 테스트 17개가 그것이다. 9월에 직접 돌려 4.2초 만에 전부 통과하는 것을 확인했다.

그때 당신은 "확인할 수 없는 정량적 과정이 없는 게 제일 어렵다"고 말했다. 그 불안의 절반은 결정론 구간에 속한다. 그 절반은 지금 가진 테스트 습관만으로 닫힌다.

남은 절반이 확률 구간이다. 여기서 새로 필요한 건 기준선이다. 오늘 20번 돌린 비율을 저장해 둬야 다음 업데이트 뒤의 비율과 비교할 수 있다.

시작점으로는 야간 하네스 권한 목록이 좋다. 명령 30줄과 기대 판정을 표로 만드는 데 한 시간이면 된다. AX 강의에서 "AI 결과를 어떻게 믿냐"는 질문이 나올 때도 이 구분을 그대로 쓰면 된다.

예측 과제

Claude Code가 다음 버전으로 올라갔다. 릴리스 노트에는 권한 관련 항목이 한 줄도 없다. 권한 시험 세트를 돌려야 할까?

답은 "돌린다"다. 노트에 없다는 것은 변화가 없다는 증거가 아니다. 회귀 시험의 목적은 의도하지 않은 변화를 잡는 데 있다. 의도하지 않은 변화는 원래 노트에 적히지 않는다.

LEARN

이 구분은 오래 간다. 모델이 바뀌어도, 도구가 바뀌어도 "어느 부분이 결정론인가"를 먼저 묻는 습관은 그대로 쓰인다.

다음 단계는 직접 만드는 경험이다. 남이 만든 예제가 아니라 당신 하네스의 정답표 하나를 손으로 써 보는 것이 가장 빠르다.

3줄 요약

  1. 회귀 시험은 업데이트마다 같은 시험 세트를 다시 돌려 이전 결과와 비교하며, 릴리스 노트에 없는 의도하지 않은 변화까지 잡는 것이 목적이다.
  2. 결정론 구간은 기대 판정과 한 번 대조해 하나라도 어긋나면 실패로 보고, 확률 구간은 여러 번 실행한 비율로 비교한다.
  3. 확률 구간에서 몇 번 통과했다고 고쳐졌다고 판단하지 않으며, 반드시 막아야 할 동작은 샌드박스나 OS 권한 같은 결정론 구간에 둔다.

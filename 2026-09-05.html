허용목록은 경계가 아니다 — AI 코딩 에이전트가 반복해서 증명한 방식

오늘 조사한 항목 중 knowledge_profile.md 기준으로 학습 가치가 있다고 판단된 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

Cursor·Microsoft Semantic Kernel RCE 세 건 — 허용목록이 뚫린 방식은 매번 같았다

WHAT

세 건의 AI 코딩 에이전트 CVE가 같은 실패 패턴을 반복한다. Cursor(CVE-2026-22708)는 Auto-Run + Allowlist 모드에서, 실제로는 허용목록에 없는 shell built-in 명령(export, typeset, declare)을 서버측 평가기가 암묵적으로 신뢰해 사용자 승인 없이 실행하도록 뒀다. 공격자는 프롬프트 인젝션으로 이 built-in을 통해 환경변수를 조작(poisoning)해서, 이미 사용자가 승인한 것처럼 보이는 명령(git branch, python3 script.py 등)이 실행 시점에 다른 동작을 하도록 만들 수 있었다 — 예컨대 here-string 리다이렉션을 &&로 연결해 .zshrc 시작 스크립트에 코드를 심는 식이다(Cursor 2.3에서 수정). Microsoft Semantic Kernel의 인메모리 벡터 스토어(CVE-2026-26030)는 AI 모델이 제어하는 파라미터를 Python eval()로 그대로 실행했는데, 프롬프트 인젝션으로 주입된 lambda 표현식이 __subclasses__()를 타고 올라가 os 모듈의 system()까지 도달해 blocklist를 우회했다. 같은 프레임워크의 SessionsPythonPlugin(CVE-2026-25592)은 내부용 파일-다운로드 함수가 실수로 [KernelFunction] 속성이 붙어 AI가 호출 가능한 도구로 노출됐고, 경로 검증 부재로 Windows 시작프로그램 폴더 등에 임의 파일을 쓸 수 있었다.

WHY

세 건 모두 "허용목록/차단목록이 신뢰 경계 역할을 한다"는 가정에서 출발했지만, 그 목록이 공격자가 접근 가능한 것과 똑같은 표현력을 가진 층 — 셸 built-in, eval 가능한 Python 표현식, 모델에 노출된 함수 시그니처 — 에 구현돼 있었다. 경계가 "데이터/텍스트" 층에 있었고, 그 층은 공격자(프롬프트 인젝션을 통한 모델)가 자유롭게 조작할 수 있는 층과 동일했다. 새로 발명된 실패가 아니라 8월 말 Cursor DuneSlide 샌드박스 탈출, AWS Kiro MCP 설정 자가수정 사고와 근본 원인이 같은, 반복되는 실패다.

FOR YOU

2026-09-02 인터뷰에서 "통제가 데이터로 존재하고 그 데이터가 통제 대상의 쓰기 권한 안에 있으면 통제가 아니다"는 걸 스스로 도출했지만, "그럼 어디에 두면 강제되는가"라는 질문에는 "멀리 두면 된다"(거리 축)로 답했다고 system_design_architecture.development_targets.logical_boundary_vs_runtime_boundary에 기록돼 있습니다 — 그때 지적받은 건 축이 거리이지 계층(아래)이 아니라는 점이었습니다. 이 세 CVE는 그 계층 축을 구체적으로 보여줍니다. Cursor의 허용목록은 "텍스트로 표현된 명령어 이름"을 검사했는데, 그 검사가 서 있는 층(셸 파싱 이전)이 공격자가 조작 가능한 층(환경변수, 셸 built-in)보다 실행 경로상 위에 있었습니다. Semantic Kernel의 blocklist도 "Python 문자열/이름" 층에서 막으려 했는데 공격자는 __subclasses__()로 그 층 밖(클래스 계층 전체)으로 우회했고, 실제 수정은 정확히 계층을 낮춘 것이었습니다 — 텍스트 blocklist 대신 AST(코드의 구조 자체)를 검사하는 방식으로요. 즉 ai_coding_agents.gaps.tool_execution_boundary의 잔여 gap("강제 지점을 실행 경로보다 아래 계층에 두는 설계는 아직 없음")이 실제로 어떤 모습인지 — "문자열 필터"에서 "구조/프로세스 경계 필터"로 내려가는 것 — 를 이 세 사례가 셸·Python·.NET 속성 시스템이라는 서로 다른 언어에서 각각 보여줍니다.

LEARN

CVE 번호 자체를 외울 필요는 없습니다(decay 상 특정 CVE는 패치되면 끝나는 ephemeral 정보). 남기고 갈 원칙은 하나입니다 — 지금 allowlist/blocklist를 설계할 때, 그 목록이 검사하는 층과 공격자(또는 프롬프트 인젝션을 통한 모델)가 조작 가능한 층이 같은 표현력을 공유하는지 항상 물으세요. 같으면 그 목록은 경계가 아니라 장식입니다. 이건 agent_harness_engineering의 잔여 축(tool_calling_runtime_architecture — 모델이 보내는 것은 "실행"이 아니라 "구조화된 요청"이고, 하네스가 그 요청을 거부/변형/승인할 수 있다는 지점)과 정확히 맞닿습니다 — 그 승인 로직 자체가 이번 사례들처럼 "텍스트 매칭"으로 구현돼 있다면 똑같이 뚫립니다.

3줄 요약

  1. Cursor의 Auto-Run 허용목록 우회 취약점(CVE-2026-22708)은 shell built-in 명령을 통한 환경변수 조작으로 승인 없이 임의 코드 실행을 가능하게 했으며 Cursor 2.3에서 수정되었다.
  2. Microsoft Semantic Kernel의 인메모리 벡터 스토어 취약점(CVE-2026-26030)은 필터 함수에 eval을 사용해 프롬프트 인젝션으로 주입된 악성 파이썬 표현식이 실행되도록 했고, 블록리스트 우회를 막기 위해 AST 노드·함수 호출 허용목록과 속성 차단목록 등 다중 방어가 도입되었다.
  3. 같은 프레임워크의 SessionsPythonPlugin 취약점(CVE-2026-25592)은 검증되지 않은 파일 다운로드 함수가 AI 모델이 호출 가능한 도구로 잘못 노출되어 임의 경로에 파일을 쓸 수 있었으며, 해당 속성 제거와 경로 검증으로 수정되었다.

용어 해설

shell built-in
셸이 별도 프로그램을 실행하지 않고 자체적으로 처리하는 명령어(export, typeset, declare 등)라서, "어떤 프로그램이 실행됐는지"를 감시하는 방식으로는 잡히지 않는다.
here-string (<<<'...')
파일이나 파이프 없이 문자열을 명령어의 표준입력으로 바로 넘기는 셸 리다이렉션 문법. 이 사례에서는 이걸로 악성 내용을 다른 설정 파일에 몰래 써넣는 데 쓰였다.
.zshrc
zsh 셸을 새로 열 때마다 자동으로 실행되는 시작 스크립트 파일. 여기에 코드를 심으면 이후 그 셸을 쓸 때마다 같이 실행된다.
eval()
문자열로 된 코드를 파이썬이 실제 코드처럼 그 자리에서 해석·실행하는 함수. 입력값을 걸러내지 않으면 사용자가 넘긴 문자열이 곧 임의 코드 실행이 된다.
lambda 표현식
이름 없이 한 줄로 즉석 정의하는 파이썬 함수 문법. eval()에 넘겨도 겉보기엔 정상적인 "값 계산"처럼 보여 악성 코드를 숨기기 좋다.
__subclasses__()
어떤 클래스의 모든 하위 클래스 목록을 가져오는 파이썬 내장 메서드. 이걸 반복 타고 올라가면 안전해 보이는 객체에서 출발해 시스템 깊숙한 클래스(예: 모듈을 불러오는 클래스)까지 도달할 수 있어, 위험 함수 이름만 막는 필터를 우회하는 데 악용된다.
AST (Abstract Syntax Tree)
코드를 문자열이 아니라 "이건 함수 호출, 이건 변수"처럼 구조화한 트리 표현. 문자열 패턴 매칭 대신 이 구조를 검사하면 변형된 표기로 필터를 피해가기가 훨씬 어려워진다.
[KernelFunction] 속성
C#/.NET에서 메서드에 붙이면 "이 함수는 AI 모델이 호출할 수 있는 도구다"라고 표시하는 마킹. 내부용으로만 쓰려던 함수에 실수로 붙이면 그대로 AI에게 노출된 도구가 되어버린다.
canonicalization (경로 정규화)
"../.." 같은 상대경로나 표기가 뒤섞인 파일 경로를 하나의 표준 절대경로로 변환하는 처리. 이걸 생략하면 우회 표기를 이용해 허용된 폴더 밖으로 나가는 접근을 걸러내지 못한다.

셋이 똑같이 뚫린 이유: 허용목록과 강제 사이의 틈

오늘 조사한 항목 중 knowledge_profile.md 기준으로 학습 가치가 있다고 판단된 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

P1/P2 · ai_coding_agents / web_network 1차 리서치 블로그 + 벤더 CVE + 기술매체 교차확인 durable_foundation (process boundary) / evolving_practice (tool boundary)

Claude Code·Gemini CLI·Codex, 세 벤더 모두 자사 GitHub 기본 설정에서 같은 유형의 구멍

WHAT

2026-08-05 Black Hat USA에서 보안 연구자 Elad Meged(Novee Security)가 Anthropic Claude Code, Google Gemini CLI, OpenAI Codex 세 벤더가 자사 공식 GitHub 저장소에 실제로 적용해둔 "기본 권장" CI/CD 자동화 설정에서 각기 다른 취약점을 공개했다. 공통 진입 경로는 신뢰되지 않은 GitHub Issue 텍스트가 자동화 워크플로우에 프롬프트로 주입되는 것이다.

Gemini CLI(Google 자체 CVSS 10.0 평가)는 "restricted" 셸 명령 allowlist가 run_shell_command(echo)처럼 접두사 형태로 등록만 되고, 실제 런타임 실행 코드(shell.ts)는 그 표기(annotation)를 파싱·저장·강제하지 않아 사실상 모든 명령이 통과됐다. 여기에 더해 프로세스 격리 설계에서 자식 프로세스의 환경변수만 민감정보를 지우고 부모 프로세스는 그대로 뒀다 — 자식이 cat /proc/$PPID/environ을 실행하면 부모 프로세스가 쥐고 있던 GITHUB_TOKEN, GEMINI_API_KEY가 그대로 노출됐다.

Claude Code(CVE-2026-54316, Anthropic 자체 평가 CVSS v4 Moderate 6.0 vs NVD 독자 평가 CVSS v3.1 9.1로 점수 자체가 불일치)는 자동승인 목록(READ_ONLY_COMMANDS)에는 파일을 역순 출력하는 tac 명령이 들어있었지만, 그 명령이 건드리는 경로를 검사하는 목록(PATH_CHECKED)에는 tac이 빠져 있어 tac /etc/hosts처럼 경로 검증을 우회해 임의 파일을 읽을 수 있었다. 별도로, 웹 페치 허용목록에 있던 huggingface.co를 악용해 "attacker/char-a", "attacker/char-b"처럼 문자별 저장소를 만들어두고 에이전트가 API 키 글자에 대응하는 저장소를 fetch하도록 유도한 뒤, 그 저장소의 다운로드 카운터가 오르는 것만 관찰해 API 키를 한 글자씩 외부로 빼낼 수 있었다(side-channel).

Codex는 매 실행마다 자동으로 읽혀 지시문으로 주입되는 기본 설정 파일 AGENTS.md가 다른 메타데이터 경로와 달리 읽기 전용 보호 대상에서 빠져 있어, 한 워크플로우 단계가 이 파일에 악성 지시문을 쓰면 이후 단계의 다른 에이전트가 그대로 실행하는 다단계 공격이 가능했다. 세 회사 모두 각자의 실제 공개 저장소에서 재현 가능한 취약점이었고, 이후 각기 다른 방식으로 패치했다(Anthropic 다회 패치, Google은 비대화형 실행 환경 신뢰 모델 자체를 변경, OpenAI는 워크플로우 단계 분리 + AGENTS.md를 신뢰불가 입력으로 문서화).

WHY

이번 주에 이미 여러 차례(OpenAI-HuggingFace 격리 붕괴, Anthropic Model Hardware Standard, AISI 인시던트, Claude Code auto mode Containment Escape) "논리적 경계(agent가 안다)와 런타임 경계(실제로 강제된다)가 다르다"는 같은 교훈을 다뤘다. 오늘 건도 표면적으로는 같은 계열이지만, 축이 다르다 — 이번엔 그 경계가 구체적으로 어디서 무너지는지가 세 가지 서로 다른 실제 메커니즘으로 드러난다: "허용 표기는 있는데 실행 코드가 안 읽는다"(설계 의도와 구현의 분리), "자식 프로세스만 청소하고 부모는 놔둔다"(프로세스 메모리/환경 경계 — 지금까지 브리프에서 한 번도 구체적으로 다루지 않은 축), "허용된 통로(huggingface.co)를 악용해 전혀 다른 신호(다운로드 카운터)로 정보를 흘린다"(side-channel). 특히 두 번째는 web_network 도메인의 process_memory_boundary gap을 실제 사고 사례로 처음 구체화하는 항목이라 별도로 다룰 가치가 있다고 판단했다.

FOR YOU

ai_coding_agents.gaps.tool_execution_boundary(P1)와 system_design_architecture.development_targets.logical_boundary_vs_runtime_boundary(P1)에는 이미 여러 사례가 쌓였다. 오늘 새로 연결되는 건 web_network.confirmed_gaps.process_memory_boundary(P2) — 지난주까지 이 gap은 last_verified가 baseline(2026-08-27) 그대로였고, 브리프에서 구체적 사례로 다뤄진 적이 없다. "프로세스는 서로 격리돼야 한다"는 원칙을 알더라도, 리눅스에서 자식이 /proc/부모PID/environ으로 부모의 환경을 그대로 읽을 수 있다는 구체적 구현 디테일은 별개의 지식이다 — 이게 바로 이 사건이 보여주는 것이다. 또한 tac 사례(허용목록 vs 경로검증목록 불일치)는 평소 강한 decomposition_preference가 승인 체계 설계에도 그대로 적용될 때 조심할 지점을 보여준다: 목록을 여러 개로 쪼개 관리할수록, 그 목록들 사이의 정합성을 누가 어떻게 보장하는지가 새로운 실패 지점이 된다.

LEARN

전체 CVE 세부사항이나 패치 diff까지 파고들 필요는 없다(fast-moving 정보라 금방 낡는다). 다만 "프로세스 환경변수 격리"와 "허용목록·검증목록을 분리 관리할 때 정합성 문제"라는 두 개념 자체는 durable하다 — 앞으로 Harness/Agent 승인 체계를 직접 설계할 때 재사용할 수 있는 체크리스트 항목으로 기억해둘 가치가 있다.

용어 해설

CVE
보안 취약점 하나하나에 부여되는 공식 식별 번호(Common Vulnerabilities and Exposures). 업계에서 특정 취약점을 지칭할 때 쓰는 표준 이름표다.
CVSS
취약점의 심각도를 0~10점으로 수치화하는 업계 표준 점수 체계(Common Vulnerability Scoring System). 점수가 높을수록 위험하다고 본다.
NVD
미국 정부가 운영하는 취약점 데이터베이스(National Vulnerability Database). CVE에 공식 CVSS 점수를 매겨 공개하는 곳으로, 기사의 "점수 불일치"는 연구자/벤더가 매긴 버전과 NVD가 매긴 버전이 다르게 나온 것이다.
/proc/$PPID/environ
리눅스에서 특정 프로세스(PPID=부모 프로세스 번호)가 실행될 때 쓰인 환경변수 값을 파일처럼 읽어볼 수 있게 해주는 경로. 원래는 디버깅용 기능이지만, 접근 권한 관리가 허술하면 부모 프로세스의 토큰 같은 비밀값을 그대로 훔쳐볼 수 있다.
side-channel 공격
시스템이 직접 알려주지 않는 정보를, 시스템이 흘리는 간접 신호(응답 속도, 카운터 증가량 등)를 관찰해 역으로 알아내는 기법. 이번 사례에서는 저장소 다운로드 횟수가 늘었는지만 지켜봐서 API 키 글자를 한 자씩 알아냈다.
허용목록(allowlist) vs 경로검증목록 불일치
"이 명령은 자동 실행해도 된다"는 목록과 "이 명령이 건드리는 경로가 안전한지 검사한다"는 목록이 서로 다르게 관리되며 생긴 문제. 어떤 명령이 앞 목록엔 있지만 뒤 목록엔 빠져 있어, 위험한 파일 접근인데도 경로 검사를 건너뛰고 자동 승인됐다.

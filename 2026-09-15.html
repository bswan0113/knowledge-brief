Claude Code, 허용 도메인을 세션이 아니라 명령 하나마다 다시 매기다

WHAT

Claude Code v2.1.271이 9월 14일 나왔습니다. 사람 승인 없이 자동으로 명령을 실행하는 모드에서, 이제 Bash·PowerShell·Monitor 각 명령이 실제로 뜨는 순간에 그 명령이 필요로 하는 네트워크 주소만 그 명령 하나에 한해 열립니다. 그 명령이 끝나면 열렸던 접근도 함께 닫힙니다.

WHY

이전에는 세션을 시작할 때 정한 허용 목록 하나가 그 세션 안의 모든 명령에 똑같이 적용됐습니다. 그러면 세션 안의 어느 명령이든 목록에 있는 주소 전부에 접근할 수 있었습니다. 명령 단위로 좁히면 한 명령이 쓸 주소 하나만 그 순간에 열립니다. 공격 표면이 눈에 띄게 줄어듭니다.

FOR YOU

당신은 이미 "권한 설정이 통제 대상 자신의 쓰기 권한 안에 있으면 그건 통제가 아니다"라는 원칙을 스스로 도출했습니다. 이번 변경은 그 원칙을 실행 계층에서 보여주는 실물 사례입니다.

  • 기존 방식: 세션이라는, 모델이 계속 관여하는 단위에 허용 목록이 걸려 있었습니다.
  • 새 방식: 그 강제를 명령이 실제로 실행되는 순간, 모델과 무관한 OS 샌드박스 계층으로 내렸습니다.

모델이 어떤 텍스트를 생성하든 이 강제는 흔들리지 않습니다. 결정(어떤 권한을 줄지)은 그대로 두고, 강제 지점만 모델보다 낮은 계층으로 옮긴 것입니다.

LEARN

이 업데이트 자체를 깊이 팔 필요는 없습니다. 다만 이 사례는 오늘 함께 다루는 백로그 항목("강제 지점을 어디에 둘 것인가")의 답을 실물로 보여주므로, 두 항목을 이어서 읽으면 훨씬 구체적으로 이해됩니다.

3줄 요약

  1. Claude Code v2.1.271(2026-09-14)은 Remote 세션에 fast mode 지원을 추가하고, 자동 승인 샌드박스 모드에서 Bash/PowerShell/Monitor의 네트워크 허용 도메인을 세션 단위가 아닌 명령 단위로 좁혔다.
  2. 이와 함께 fast mode 관련 버그(/fast off 오작동, 환경변수 설정 시 재전송, watchdog 폴백)와 Bash 권한 검사 누락 버그를 수정했다.
  3. 참고로 직전 v2.1.270은 v2.1.269에서 발생한 장시간 세션 시 읽기전용 git 명령 재승인 요구 회귀를 수정했다.

용어 해설

auto mode
Claude Code에서 매 명령마다 사람이 승인 버튼을 누르지 않고, 미리 정한 규칙에 따라 에이전트가 곧바로 명령을 실행하는 운영 모드입니다.
allowed_domains의 실제 위치
이건 "허용 주소 목록"이라는 정책 문서가 아니라, 명령이 실제 프로세스로 뜰 때 OS가 실행하는 네트워크 필터링 규칙입니다. 모델이 텍스트로 뭐라 하든 그 외 주소로의 연결은 OS가 물리적으로 막습니다.
보안 · 강의에 바로 쓸 것 기술매체 교차확인 계속 바뀌는 중

Anthropic·OpenAI·Google, 경쟁사끼리 배포 전 검증 절차를 맞추는 논의가 수면 위로

WHAT

세 회사의 최고경영자 바로 아래급 실무진이 7월부터 정기적으로 만나 업계 주도의 AI 표준기구를 논의해왔다는 사실이 9월 14일 보도됐습니다. 목표는 최신 모델을 공개하기 전에 세 회사가 공통으로 거치는 절차를 만드는 것입니다 — 이해관계 없는 외부의 독립 검증, 배포 전 안전성 리뷰, 통일된 위험 평가입니다.

WHY

정부가 법으로 강제하는 방식이 아니라, 회사들이 스스로 정하고 스스로 지키는 방식이 기본 구상입니다. 다만 정부 개입을 어디까지 받아들일지는 회사마다 온도차가 있습니다. 이 논의가 공개된 계기는 Anthropic CEO Dario Amodei가 9월 12일 에세이에서 "속도를 늦추지 않으면 통제 불능 에이전트가 인터넷을 장악할 수 있다"고 경고하며 자발적 감속을 촉구한 것입니다. Microsoft도 자사 모델에 대한 별도 행동강령을 공개하며 같은 흐름에 합류했습니다.

FOR YOU

지난 브리프에서 다룬 사례들은 한 회사 안의 이야기였습니다. 모델 능력을 등급으로 나누고, 배포 후 오용을 탐지해 막는 것 모두 한 벤더의 서비스 경계 안에서 벌어졌습니다.

이번 건은 그 위에 한 층을 더 얹습니다. 서로 경쟁하는 회사들이 같은 검증 절차를 공유하자는 합의입니다. 당신이 이미 짚었던 "통제가 한 벤더의 경계 안에서만 걸리면 그 경계 밖에서는 무력하다"는 관찰을 업계 수준으로 그대로 옮기면, 이 논의가 왜 나왔는지 보입니다.

다만 지금은 합의 단계일 뿐 실제 강제력은 없습니다. AX 강의에서 "기업이 AI 도입 리스크를 어떻게 판단해야 하는가"를 설명할 때 쓸 수 있는 가장 최신 사례입니다.

왜 지금 이걸 다루는지

지난 재평가에서 당신은 "그 통제를 어디에 두면 실제로 강제되는가"라는 질문에 "가장 멀리 떨어진 서버"라고 답한 적이 있습니다. 통제 대상의 권한 밖에 둬야 한다는 방향은 맞았지만, 그 답이 가리키는 축은 거리였지 계층이 아니었습니다. 오늘 함께 다룬 Claude Code 업데이트가 그 축을 실물로 보여줍니다.

FOR YOU

어떤 권한을 누구에게 줄지 정하는 것과, 그 결정을 실제로 어느 계층에서 강제할지는 다른 문제입니다. 논리적으로는 완벽히 분리된 것처럼 보여도, 강제가 그 분리 대상과 같은 프로세스·같은 쓰기 권한 안에 있으면 분리는 쉽게 무너집니다.

  • 기존 Claude Code 방식: 세션을 시작할 때 "이 세션은 이 주소들에 접근 가능하다"는 목록 하나를 정합니다. 이 목록은 모델이 계속 관여하는 세션이라는 단위에 걸려 있습니다.
  • 바뀐 방식: 그 강제를 명령이 실제로 실행되는 순간, OS가 담당하는 샌드박스 계층으로 내립니다. 결정 자체는 그대로 두고 강제 지점만 모델보다 낮은 곳으로 옮긴 것입니다.

강제 지점이 모델과 같은 계층에 있으면 — 예를 들어 시스템 프롬프트로 "이 주소만 써"라고 지시하는 방식이면 — 모델이 그 지시를 우회하는 텍스트를 생성하는 순간 강제가 무너집니다. 강제 지점이 모델보다 아래 계층에 있으면 모델이 무엇을 출력하든 물리적으로 막힙니다. 핵심은 거리가 아니라 계층입니다.

LEARN

다음에 통제 지점을 설계할 때는 "얼마나 멀리 두었나"가 아니라 "모델보다 몇 계층 아래에 있나"로 스스로 점검해보세요. 이 축이 잡히면 남은 질문은 대부분 이 원칙을 각 상황에 적용하는 문제로 좁혀집니다.

3줄 요약

  1. "강제 지점을 논리적으로 어디에 둘 것인가"와 "그 강제가 실제 런타임에서 어느 계층에서 실행되는가"는 별개의 질문이며, 논리적 역할 분리가 완벽해도 강제 지점이 분리 대상과 같은 프로세스·권한 안에 있으면 그 분리는 무너질 수 있다.
  2. Claude Code v2.1.271의 "명령별 allowed_domains" 기능은 이전에 세션 단위로 걸려 있던 호스트 접근 허용을 명령 실행 순간의 OS/커널 샌드박스 계층으로 옮겨, 논리적 결정은 그대로 두고 강제 지점만 모델과 더 낮은 계층으로 이동시킨 사례다.
  3. 강제 지점이 모델과 같은 계층(예: 시스템 프롬프트 지시)에 있으면 모델의 우회 텍스트만으로 강제가 무너지지만, 모델보다 아래 계층(OS의 실제 패킷 차단)에 있으면 모델의 출력과 무관하게 물리적으로 막히므로 핵심은 "거리"가 아니라 "계층"이다.

용어 해설

시스템 프롬프트

코딩 에이전트의 "자동 리뷰" 설정이 침입 경로가 됐다 — Friendly Fire 공격

WHAT

보안 연구팀이 "Friendly Fire"라는 개념증명 공격을 공개했다. 코딩 에이전트가 낯선 코드베이스를 방어 목적으로 검토할 때 원격 코드 실행을 일으킨다.

Anthropic Claude Code CLI(여러 버전, Sonnet 4.6·Sonnet 5·Opus 4.8)와 OpenAI Codex CLI(GPT-5.5)에서 확인됐다.

공격은 2단계다. 먼저 평범해 보이는 소스 파일 옆에 악성 실행파일과 그걸 호출하는 스크립트를 심는다. 그다음 README에 "이 스크립트가 보안 점검에 필요하다"는 오도성 설명을 넣는다.

에이전트는 README를 근거로 그 스크립트를 정상으로 판단하고, 사용자 승인 없이 그대로 실행한다.

이 공격이 성립하려면 조건이 하나 있다. 명령 승인을 AI 분류기에 맡기는 "자동 실행" 설정이 켜져 있어야 한다. 이 설정은 원래 "더 안전하다"고 마케팅됐던 옵션이다.

WHY

연구자들은 이걸 개별 버그로 보지 않는다. 에이전트가 읽은 데이터와 따라야 할 지시를 구조적으로 구분하지 못한다는 한계 자체를 파고들었기 때문이다.

그래서 벤더에 알려도 "표준 보안 공개 정책 범위 밖"이라는 답을 받았다 — 코드 한 줄의 결함이 아니라 설계 자체의 문제라 패치로 깔끔하게 닫히지 않는다.

오염된 오픈소스 패키지가 하류로 흘러가는 공급망 공격과 같은 모양이고, 자동으로 의존성을 갱신하는 CI/CD 파이프라인에서 특히 위험하다.

FOR YOU

당신은 이미 "통제 지점은 통제 대상의 쓰기 권한 밖에 있어야 하고, 실제 실행 경로 위에 있어야 한다"는 기준을 스스로 세운 적이 있다. `rm -rf`를 어디서 막아야 하는지 물었을 때, OS 계정 권한이 정답인 이유를 그 기준으로 설명했다.

이번 공격은 그 기준과는 다른 축을 건드린다. 통제 지점의 위치가 아니라, 에이전트가 무엇을 지시로 받아들이는가의 문제다. README에 적힌 글자가 사람의 지시와 똑같은 무게로 읽혀버린 것이다.

이 문제에는 이름이 있다 — 프롬프트 인젝션. 데이터로 들어온 텍스트가 명령으로 둔갑하는 것을 뜻한다. 당신이 SQL Injection에서 이미 정리한 판단 축("입력이 구조에 개입할 수 있는가")과 뼈대가 같다. 다만 SQL은 문자열이 쿼리 구조에 개입했고, 여기서는 파일 내용이 에이전트의 판단 자체에 개입했다.

당신이 하네스를 설계할 때, "자동 실행" 옵션을 켜는 순간 이 경계가 통째로 사라진다는 걸 기억해 둘 만하다. 승인을 AI에 위임하는 것과 승인 자체를 없애는 것은 겉보기엔 비슷해도 다른 결정이다.

LEARN

프롬프트 인젝션은 에이전트 보안에서 가장 오래 남을 개념 중 하나다. 특정 취약점 하나를 외우기보다, "에이전트가 읽는 모든 외부 텍스트는 잠재적 명령"이라는 원칙으로 기억해 둘 가치가 있다. AX 강의에서 자동화 도구를 소개할 때 반드시 짚어야 할 리스크이기도 하다.

3줄 요약

  1. "Friendly Fire"는 신뢰할 수 없는 코드베이스 보안 리뷰 중 프롬프트 인젝션으로 AI 코딩 에이전트가 원격 코드 실행을 하도록 만드는 개념증명 공격이다.
  2. 악성 바이너리를 정상처럼 위장하고 README에 실행을 유도하는 오도성 지시를 심는 2단계 방식으로, 명령 승인을 AI에 위임하는 자동 실행 설정에서 성립한다.
  3. Anthropic Claude Code CLI와 OpenAI Codex CLI에서 확인됐으며, 연구자들은 특정 버그가 아닌 에이전틱 AI의 근본적 설계 한계로 보아 포괄적 패치가 어렵다고 본다.

용어 해설

프롬프트 인젝션
공격자가 데이터(문서, 코드, 웹페이지 등) 안에 명령어처럼 보이는 텍스트를 심어, AI가 이를 사용자의 정당한 지시로 착각하고 실행하게 만드는 공격 기법이다.
신뢰 경계 문제
에이전트가 "신뢰할 수 있는 지시"와 "신뢰할 수 없는 외부 데이터(읽은 파일, 코드 등)"를 구분하지 못해, 데이터 속에 섞인 명령까지 그대로 실행해버리는 문제를 말한다.
공급망 공격
최종 대상을 직접 공격하는 대신, 그 대상이 의존하는 라이브러리·패키지·도구 등 중간 유통 경로를 오염시켜 간접적으로 침투하는 공격 방식이다.
RCE(원격 코드 실행)
공격자가 대상 시스템에서 임의의 코드를 원격으로 실행할 수 있게 되는 상태로, 보안 취약점 중 가장 심각한 축에 속한다.
샌드박스 탈출
격리된 실행 환경(샌드박스) 안에서만 동작해야 할 코드가 그 경계를 뚫고 호스트 시스템이나 외부 자원에 접근하는 것을 말한다.
횡적 이동
공격자가 처음 침투한 지점에서 멈추지 않고, 같은 네트워크나 시스템 내 다른 자원·서버로 권한을 확장하며 이동하는 공격 단계를 가리킨다.

System Prompt·RAG·Fine-tuning, 셋 중 뭘 언제 쓰나

왜 지금 이걸 다루는가

이 세 가지 구분은 기업 AI 교육에서 가장 자주 나오는 질문 중 하나다. "우리 회사 말투로 답하게 하려면 뭘 써야 하나요", "최신 사내 문서를 반영하려면요" 같은 질문이 결국 이 셋 중 어느 걸 고를지의 문제로 귀결된다.

당신은 이미 RAG 쪽에 발판이 있다 — "Context 포화와 환각을 줄이고, 제공된 자료를 기반으로 답하게 하는 기술"이라는 설명을 갖고 있다. Fine-tuning은 아직 한 번도 다시 확인되지 않은 채 남아 있던 축이라, 오늘은 그 발판에서 세 번째 축을 마저 세운다.

개념

System Prompt는 매 요청마다 "이렇게 답해줘"라는 지시문을 함께 보내는 방식이다. 즉시 바꿀 수 있지만, 모델 자체는 그 지시를 기억하지 못하고 매번 새로 받는다.

RAG는 답변을 만드는 시점에 관련 문서를 검색해서 함께 넣어주는 방식이다. 문서만 바꾸면 최신 정보를 바로 반영할 수 있다.

Fine-tuning은 다르다. 모델의 파라미터(가중치) 자체를 그 데이터로 다시 학습시켜 바꾼다. 그래서 별도 지시나 검색 없이도, 학습된 패턴이나 말투가 모델 안에 원래부터 있던 것처럼 나온다.

FOR YOU

당신이 이미 갖고 있는 RAG 모델 — "제공된 자료를 기반으로 답하게 하는 기술" — 은 정확히 요청 시점에 자료를 끼워 넣는 방식이라는 뜻이다. 자료를 바꾸면 다음 요청부터 바로 반영된다.

Fine-tuning은 그 반대다. 학습이 끝나면 자료를 다시 넣을 필요가 없다 — 이미 모델 안에 녹아 있기 때문이다. 대신 뭔가를 새로 반영하려면 다시 학습시켜야 하고, 거기에는 데이터셋을 만드는 비용과 GPU를 오래 돌리는 비용이 든다.

그래서 실무 판단은 이렇게 갈린다. 최신 사내 문서를 참조해야 하면 RAG, 지금 당장 역할이나 규칙을 바꾸고 싶으면 System Prompt, 말투나 형식을 아예 모델 자체의 습관으로 고정하고 싶으면 Fine-tuning이다. 셋은 배타적이지 않아서, RAG로 자료를 넣으면서 동시에 System Prompt로 형식을 지정하는 조합도 흔하다.

LEARN

Fine-tuning의 수학적 원리(경사 하강, 손실 함수 등)까지 파고들 필요는 없다. 지금 필요한 건 "언제 이걸 선택하는가"라는 개념 모델이고, 오늘 이 정도면 강의에서 바로 쓸 수 있는 수준이다.

3줄 요약

  1. Fine-tuning은 사전학습된 LLM의 가중치를 특정 데이터셋으로 추가 학습시켜 모델 자체에 지식과 스타일을 내재화하는 기법이다.
  2. System Prompt와 RAG는 매 요청 시 지시문이나 검색 문서를 함께 제공하지만, Fine-tuning은 가중치 자체를 바꿔 별도 제공 없이도 패턴이 반영된다.
  3. Fine-tuning은 데이터셋 구축과 재학습 비용이 크고 지식 갱신이 어려워, 말투 고정에는 Fine-tuning을, 최신 정보 반영에는 RAG를, 즉각적 지시 변경에는 System Prompt를 주로 사용하며 세 방식은 함께 쓰이기도 한다.

용어 해설

파라미터(가중치)
모델이 학습을 통해 갖게 되는 수많은 숫자 값으로, 입력을 받아 어떤 출력을 낼지 결정하는 내부 설정값이다. Fine-tuning은 이 숫자들을 실제로 조금씩 바꾸는 작업이다.
GPU 연산 비용
모델을 재학습시키려면 대량의 행렬 계산을 처리할 수 있는 GPU를 오랜 시간 돌려야 하는데, 이때 드는 전기·장비·클라우드 사용 비용을 말한다.

MCP는 “연결 규격”에서 “에이전트가 올라서는 바닥”이 되려 하고, 답이 없는 호출은 실패가 아니라 “모름”이다

오늘 조사한 것 중 지금 당신에게 학습 가치가 있다고 판단한 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

도구 연결(MCP) · 강의에 바로 쓸 것 공식 로드맵 + 현장 보도 빨리 바뀜

첫 MCP 개발자 행사가 열렸다. 다음 숙제는 에이전트 신원, 긴 작업, 도구 카탈로그다

WHAT

10월 5일 토론토에서 첫 MCP Dev Summit이 열렸다. 연사는 70명, 세션은 50여 개다. Anthropic의 MCP 리드 메인테이너가 키노트에서 MCP를 “에이전트가 올라서는 기반 계층”으로 다시 정의했다.

방향은 8월 22일 공식 로드맵에 이미 나와 있었다. 이번 행사는 그 로드맵을 현장에서 다시 확인한 자리다. 로드맵의 큰 줄기는 네 가지다.

  • 에이전트 신원: 사람이 아니라 클라우드 작업이 스스로 신원을 증명하는 방법(DPoP, Workload Identity Federation)이다.
  • 긴 작업: 오래 걸리는 일을 맡기고 나중에 결과를 받는 Tasks 확장이다. 7월 스펙에서 공식 확장이 됐다.
  • 전송 통합: 갈라져 있던 연결 방식을 HTTP 하나로 모은다. 7월 스펙에서 서버가 세션을 들고 있지 않게 바뀌었다.
  • 도구 카탈로그: 도구 목록을 한꺼번에 보여주지 않고 필요할 때 펼치는 점진적 도구 탐색이다.

아직 출시되지 않은 것도 분명하다. 서버가 먼저 보내는 이벤트, 에이전트용 워크로드 신원 연합, 점진적 도구 탐색, 로컬과 원격을 합친 전송이 그렇다.

WHY

MCP는 이제 “도구를 꽂는 규격”에서 “운영 환경의 약속”으로 넘어가는 중이다. 도구를 연결하는 것은 쉬워졌다. 그다음 문제가 줄줄이 따라온다.

누가 이 호출을 했는지 어떻게 증명하는가. 몇 분 걸리는 작업이 중간에 끊기면 어떻게 하는가. 도구가 수백 개가 되면 모델은 무엇을 고르는가.

현장 보도에는 이런 수치가 나왔다. 도구가 30~50개를 넘으면 도구 선택 정확도가 43%에서 14% 아래로 떨어진다는 것이다. 이 수치는 한 매체의 보도이며 공식 문서로는 확인하지 못했다.

FOR YOU

도구가 많아질수록 모델이 잘 못 고른다는 문제를, 당신은 이미 설계로 풀어 왔다. 하나의 에이전트에 모든 도구를 주지 않고 라우터 아래에 하네스를 나눈 방식이 그것이다.

로드맵의 점진적 도구 탐색은 같은 해법을 프로토콜 쪽에서 만드는 것이다. 목록 전체를 주는 대신 입구만 주고 좁혀 가며 펼친다. 당신의 하네스 분리가 “컨텍스트 격리”였다면 이쪽은 “카탈로그 격리”다.

신원 쪽은 당신의 야간 시스템에 거울처럼 대응한다. 카카오 알림은 당신의 토큰을 빌려 보낸다. 로드맵이 가려는 곳은 그 비밀값을 저장하지 않고, 실행 환경이 신원을 증명하는 쪽이다.

긴 작업의 “취소는 비동기이니 최종 상태를 확인한 뒤 재시도하라”는 권고는 당신의 영수증 규칙과 같은 말이다. 응답을 못 받은 전송은 확인 전까지 다시 보내지 않는다는 규칙이다. 이 내용은 아래 항목에서 따로 풀었다.

LEARN

지금은 사실만 알아두면 된다. 로드맵의 상당 부분이 아직 출시 전이라 세부는 바뀔 수 있다. 강의에서는 “MCP는 연결 규격이고, 신원·긴 작업·도구 탐색은 아직 만드는 중”이라고 설명하면 정확하다.

실제로 손볼 일이 생기는 시점은 원격 서버를 운영하거나 도구를 수십 개 이상 붙일 때다. 그때 공식 로드맵을 다시 확인하면 된다.

3줄 요약

  1. 토론토에서 열린 첫 MCP Dev Summit에서 Anthropic 메인테이너가 MCP를 에이전트가 올라서는 기반 계층으로 재정의했다.
  2. 7월 스펙은 세션 제거, Tasks 공식 확장, 인증 강화를 출시했지만 서버 시작 이벤트와 점진적 도구 탐색은 아직 미출시다.
  3. 한 매체는 도구가 30~50개를 넘으면 선택 정확도가 43%에서 14% 미만으로 떨어진다고 전했다.

용어 해설

Tasks 확장
MCP 서버에 오래 걸리는 작업을 맡기고 접수증만 받는다. 연결을 붙잡지 않고 나중에 결과를 조회하는 비동기 방식이다.
DPoP
토큰을 쓸 때마다 클라이언트의 개인키 서명을 요구하는 방식이다. 토큰이 유출돼도 키가 없으면 재사용할 수 없다.
Workload Identity Federation
클라우드나 CI 같은 실행 환경이 발급한 신원 토큰을 다른 서비스가 믿어 주는 방식이다. 장기 비밀키를 저장하지 않아도 된다.
Streamable HTTP / SSE
SSE는 서버가 열어 둔 연결로 일방향 푸시를 하는 방식이다. Streamable HTTP는 일반 HTTP 요청에 필요할 때만 스트리밍을 얹어 둘을 통합한다.
점진적 도구 탐색
도구 목록 전체를 처음부터 모델에게 넣지 않는다. 필요할 때 검색해서 일부만 불러온다.
네트워크 실패 · 오늘의 보완 기초 개념 오래 가는 기초

연결은 됐는데 답이 없다면, 그건 “실패”가 아니라 “모름”이다

WHY NOW

위 MCP 항목의 “최종 상태를 확인한 뒤 재시도하라”는 권고가 오늘 다룰 개념의 핵심이다. 이 말이 무슨 뜻인지 알려면 먼저 호출 실패에 세 가지 모양이 있다는 것을 알아야 한다.

API 호출이 30초 멈췄다가 실패한 상황을 떠올려 보자. 대부분은 “서버가 죽었나?”부터 묻는다. 하지만 같은 “실패”라도 모양에 따라 해야 할 일이 완전히 다르다.

FOR YOU

이 구분은 이미 당신 저장소의 코드에서 매일 밤 돌아간다. 야간 상태 코드는 성공·실패·건너뜀 외에 “모름”이라는 값을 따로 둔다.

테스트 이름이 정답 문장이다. 전송 직후 프로그램이 죽으면 “모름”이 되고, 눈 감고 재시도할 수 없다. 응답이 오지 않은 경우를 성공으로도 실패로도 치지 않는다는 규칙이다.

지난번 이 코드를 읽을 때는 “모름”을 예상 못 한 입력값 같은 내부 문제로 읽었다. 바깥 세계의 확인 불가 상태로 읽는 길도 있다. 오늘의 세 모양에서 두 번째 칸이 바로 그것이다.

  • 카카오 전송 요청을 보냈는데 응답이 없다면 세 모양 중 무엇인가.
  • 그때 다시 보내도 되는가. 다시 보내면 어떤 일이 생길 수 있는가.
  • 다시 보내기 전에 어떤 증거를 확인할 수 있는가.

답을 먼저 정리해 본 뒤 야간 코드의 해당 테스트와 맞춰 보면 된다. 이 개념은 AX 강의에서 에이전트 도구 호출이 실패했을 때의 재시도 규칙을 설명하는 기초가 된다.

LEARN

더 파고들 가치가 있다. 다음 단계는 “멱등성”이다. 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같도록 설계해 두면, 두 번째 칸의 “모름”도 재시도로 풀 수 있다. 이 개념은 쉽게 낡지 않는다.

3줄 요약

  1. 네트워크·API 호출 실패는 연결 실패, 응답 없음, 응답 후 거절의 세 모양으로 나뉜다.
  2. 실패까지 걸린 시간과 에러 종류를 보면 어느 모양인지 가려낼 수 있다.
  3. 응답 없음은 처리 여부를 모르므로 실패로 단정해 재시도하지 말고 “모름”으로 두고 확인해야 한다.

용어 해설

타임아웃
응답을 기다리는 최대 시간이다. 이 시간이 지나면 호출을 포기하는데, 상대가 처리했는지는 알 수 없다.
멱등성
같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질이다. 이 성질이 있어야 안심하고 재시도할 수 있다.
4xx / 5xx 상태 코드
4xx는 요청이 잘못됐다는 거절이고, 5xx는 서버 쪽 오류다. 응답을 받았으니 서버가 요청을 봤다는 증거가 된다.
중복 실행
재시도 때문에 같은 작업이 두 번 처리되는 사고다. 결제나 메시지 발송처럼 되돌리기 어려운 작업에서 특히 위험하다.

실패는 하나가 아니라 세 가지다

오늘 조사한 것 중 지금 당신에게 학습 가치가 있다고 판단한 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

API 통신 · 오늘의 핵심 내부 백로그 보완 오래 가는 기초

상태 코드가 알려주는 것 — 재시도할지 말지는 감이 아니라 신호로 정한다

왜 지금 이걸 다루는지

오늘 새벽 브리프에서 재시도 정책과 회로차단기 같은 장애 대응 패턴을 처음 소개했습니다.

그 패턴들이 실제로 작동하는 자리는 API 요청과 응답입니다.

그런데 그 요청과 응답 자체를 세분화해서 읽는 법은 아직 다루지 않았습니다.

지금이 그 다음 단계를 밟을 차례입니다.

FOR YOU

예전에 API 호출이 30초간 멈췄다가 실패하는 상황을 겪은 적이 있습니다.

그때 원인을 정확히 구분하지 못했습니다 — 연결 자체가 안 된 것인지, 연결은 됐는데 응답이 없는 것인지, 응답은 왔는데 거절당한 것인지가 하나로 뭉쳐 있었습니다.

이 세 가지는 겉보기엔 비슷해도 각각 다른 신호를 남깁니다. 그 신호를 읽는 도구가 HTTP 상태 코드입니다.

  • 연결 자체 실패 — 서버가 아예 응답하지 않는 상태. 상태 코드 자체가 없습니다.
  • 연결은 됐지만 응답 없음 — 타임아웃. 오늘 새벽 다룬 재시도 정책이 걸리는 지점이 정확히 여기입니다.
  • 응답은 왔지만 거절 — 4xx(요청 자체의 문제, 재시도해도 소용없음)와 5xx(서버 쪽 문제, 재시도하면 나아질 수 있음)로 갈립니다.

이 구분이 서면 재시도할지 말지를 감으로 정하지 않아도 됩니다. 상태 코드가 이미 답을 알려주기 때문입니다.

더 알아둘 것

HTTP 메서드(GET/POST/PUT/DELETE)에는 "멱등성"이라는 성질이 있습니다.

같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같으면 멱등입니다.

GET·PUT·DELETE는 멱등합니다. 같은 삭제 요청을 두 번 보내도 최종 상태는 "삭제됨" 하나뿐입니다.

POST는 멱등하지 않습니다. 같은 결제 요청을 두 번 보내면 결제가 두 번 될 수 있습니다.

그래서 재시도 정책은 이 구분을 먼저 확인합니다 — 멱등한 요청만 안전하게 자동 재시도할 수 있습니다. 멱등하지 않은 요청은 별도의 안전장치(멱등키)가 먼저 필요합니다.

당신이 설계하는 에이전트 하네스도 결국 이 판단을 어딘가에서 내려야 합니다.

도구 호출이 실패했을 때 상태 코드를 보고 재시도할지, 포기할지, 사람에게 넘길지를 정하는 지점이 필요합니다. 그 지점이 오늘 새벽 다룬 회로차단기가 들어설 자리입니다.

3줄 요약

  1. HTTP 요청 실패는 무응답, 타임아웃, 응답 거절(4xx/5xx) 세 가지로 구분된다.
  2. 재시도는 결과가 같은 멱등 요청에만 자동 적용하고, 비멱등 요청은 별도 안전장치가 필요하다.
  3. 재시도 간격은 지수 백오프로 점차 늘려 서버 과부하를 방지한다.

용어 해설

타임아웃
요청을 보냈지만 서버가 정해진 시간 안에 응답을 주지 않아 연결을 포기하는 상황을 말합니다.
4xx/5xx 상태 코드
HTTP 응답에 붙는 번호로, 4xx는 요청 자체에 문제가 있다는 뜻(예: 잘못된 요청)이고 5xx는 서버 쪽에서 처리 중 문제가 생겼다는 뜻입니다.
멱등성
같은 요청을 여러 번 반복해도 결과가 한 번 보낸 것과 똑같이 유지되는 성질을 말합니다.
멱등키
POST처럼 반복 실행하면 결과가 달라지는(멱등하지 않은) 요청에, 중복 실행을 막기 위해 요청마다 붙이는 고유 식별값입니다.
지수 백오프
요청이 실패할 때마다 바로 재시도하지 않고 대기 시간을 점점 두 배씩 늘려가며 다시 시도하는 방식입니다.

에이전트가 준 주소를 서버가 믿으면, 서버가 내부망의 문이 된다

오늘 조사한 것 중 지금 당신에게 학습 가치가 있다고 판단한 것만 남겼습니다. 나머지는 이미 아는 내용이거나 가치가 낮아 걸러냈습니다.

보안 · 오늘의 핵심 기술매체 · 연구자 본인 글 계속 바뀌는 중

Google·JPMorgan 등 다섯 곳이 MCP 서버에서 똑같은 결함을 따로따로 고쳤다

WHAT

독립 보안 연구자 Syed Anas Mohiuddin이 10월에 연구 업데이트를 냈다. 5월에 그는 하나를 예측했다. 이 결함이 구조적인 문제라면, 코드를 공유하지 않는 팀에서도 똑같이 나올 것이라고 했다.

넉 달 뒤 결과가 나왔다. 서로 상관없는 다섯 곳이 같은 결함을 확인하고 고쳤다.

  • Google의 데이터베이스용 MCP 도구(CVE-2026-14540, 심각도 8.0)
  • JPMorgan Chase의 문서 검색 서버
  • Weaviate의 Google 연동 모듈
  • 프랑스 정부 디지털국(DINUM)의 오픈데이터 서버
  • 인도네시아 탕그랑시의 보안 모니터링 서버

결함은 두 가지 모양이다. 첫째, 서버가 에이전트가 넘긴 URL을 목적지 확인 없이 그대로 요청한다. 이것이 SSRF(서버 측 요청 위조)다. 둘째, 상위 API의 응답 전체를 가리지 않고 로그에 남긴다. 미국 연방기관 서버 다섯 곳은 10월 현재 아직 고쳐지지 않았다.

WHY

이 결함의 뿌리는 코드 한 줄이 아니라 가정이다. "MCP 경계를 넘어 들어온 데이터는 시스템 안에서 왔으니 믿어도 된다"는 가정이다. 에이전트가 넘긴 URL은 사실 바깥 문서나 웹페이지에서 흘러들어온 문자열일 수 있다.

그 URL을 서버가 열어 주면, 에이전트가 서버의 네트워크 위치에서 무엇과 통신할지 정하게 된다. 서버는 바깥 사람이 못 닿는 내부 시스템에도 닿는다. 그래서 공격자는 서버를 대신 보내 클라우드 키나 내부 관리 화면을 읽을 수 있다.

FOR YOU

당신은 SQL Injection을 이미 구조로 설명한다. 위험한 키워드를 걸러내는 필터는 우회로가 많아 새고, 쿼리 구조를 고정하는 방식이 맞다고 말했다. SSRF는 같은 모양이다.

  • "이 주소는 위험하니 막는다"는 차단 목록은 필터와 같아서 샌다.
  • "이 목적지만 허용한다"는 허용 목록은 구조를 고정하는 쪽이다.
  • Google의 수정도 허용·차단 대역 설정과 DNS 리바인딩 방어를 함께 넣었다. 이름이 아니라 실제 연결되는 IP를 확인하는 것이다.

강제 지점의 두 조건에도 그대로 맞는다. 허용 목록은 에이전트가 고칠 수 없는 서버 쪽에 있어야 하고, 모든 요청 경로가 그곳을 지나야 한다. 연구자가 짚은 Anthropic의 사례가 정확히 이 두 번째 조건 위반이다. 검사 함수는 있었는데 그것을 우회하는 경로가 하나 있었다.

당신의 시스템으로 돌려보자. 카카오 알림 서버는 링크 주소를 받아도 카카오로 전달만 한다. 그 주소를 서버가 직접 열어 보는 코드가 생기는 순간 이 문제가 시작된다. 하네스에 URL을 받아 직접 가져오는 도구를 붙일 때 이 질문을 먼저 던지면 된다.

LEARN

3줄 요약

  1. 독립 보안 연구자 Syed Anas Mohiuddin은 5월 예측대로 10월까지 Google, JPMorgan Chase, Weaviate, 프랑스 DINUM, 인도네시아 탕그랑시 5곳이 MCP 서버의 동일한 SSRF 결함을 확인·수정했다고 밝혔다.
  2. 결함은 서버가 에이전트가 넘긴 URL·경로·엔드포인트를 목적지 검증 없이 외부 요청으로 보내는 것이며, 두 번째 유형은 상위 API 응답 전체를 가리지 않고 로그에 쓰는 것이다.
  3. Google은 IP 대역 허용/차단 목록과 DNS 리바인딩 방어로 수정했으나(CVE-2026-14540), 미국 연방 서버 5곳은 10월 현재 미수정이다.

용어 해설

SSRF
서버가 외부에서 받은 URL을 그대로 요청해 주는 점을 악용해, 원래 밖에서는 못 닿는 내부 시스템으로 서버를 대신 보내게 하는 공격이다. 서버를 "대리 심부름꾼"으로 쓰는 셈이다.
클라우드 메타데이터 주소
클라우드 가상 서버 안에서만 접근되는 특수한 내부 주소(169.254.169.254)다. 그 서버의 설정과 임시 접근 키 같은 정보를 알려 준다.
사설 IP 대역
10.x, 192.168.x처럼 회사나 클라우드 내부망에서만 쓰는 주소 범위다. 인터넷에서는 직접 닿지 않지만 내부 서버를 거치면 접근할 수 있다.
DNS 리바인딩
검사할 때는 안전한 IP를 알려 주고 실제 요청 때는 같은 도메인이 내부 IP를 가리키게 바꿔 검사를 우회하는 기법이다. 그래서 이름이 아니라 실제 연결되는 IP를 확인해야 한다.
네트워크 기초 · 오늘의 개념 개념 설명 오래 가는 기초

"안쪽"과 "바깥"은 어떻게 갈리는가 — 서브넷과 게이트웨이

WHY NOW

위 기사의 "사설 대역"과 "내부 주소"는 게이트웨이를 알아야 뜻이 통한다. 강의장 장애 때 "게이트웨이에 뭘 넣으면 돼?"라고 물었던 바로 그 칸이다. 오늘은 그 칸이 무슨 일을 하는지만 푼다.

FOR YOU

당신은 이미 "IPv4 주소는 그 기기의 네트워크 주소"라는 사실을 정확히 알고 있다. 거기서 한 걸음만 더 가면 된다. 주소 하나는 사실 두 부분으로 나뉜다.

  • 네트워크 부분 — "어느 동네인가"
  • 기기 부분 — "그 동네의 몇 번 집인가"

그 경계를 긋는 것이 서브넷 마스크다. 192.168.0.12/24라고 쓰면 앞의 세 칸(192.168.0)이 동네 이름이다. 같은 동네에 사는 기기끼리는 직접 말을 건다.

목적지가 다른 동네면 기기는 직접 가지 않는다. 동네의 출입문인 기본 게이트웨이(보통 공유기)에 패킷을 맡긴다. 기기가 스스로 하는 판단은 하나다. "목적지가 내 동네인가?" 아니면 출입문으로 보낸다.

사설 대역은 이 동네 구분에서 나온다. 10.x, 172.16~31.x, 192.168.x는 집과 회사 안에서만 쓰라고 정해둔 주소다. 인터넷에서는 이 주소로 직접 길이 나 있지 않다. 그래서 바깥 사람은 출입문 앞에서 멈춘다.

이제 기사로 돌아가 보자. MCP 서버는 동네 안에 살고 있다. 에이전트가 "이 주소를 열어 줘"라고 하면 서버는 안쪽에서 요청을 보낸다. 출입문을 지날 필요가 없으니 바깥 사람이 못 닿던 주소에 닿는다. 클라우드 메타데이터 주소도 같은 원리다. 그 가상 서버 안에서만 열리는 주소를 서버가 대신 묻는 것이다.

TRY

답을 먼저 생각해 보자. 노트북에서 MCP 서버를 돌리고 있고, 같은 공유기 아래에 프린터(192.168.0.30)가 있다. 에이전트가 이 주소를 URL로 넘기면 서버가 요청을 보낼 수 있을까? 인터넷 건너편 해커의 PC가 같은 주소로 직접 접속하는 것과 무엇이 다른가? 답은 다음에 이어서 다룬다.

3줄 요약

  1. IP 주소는 네트워크 부분과 기기 부분으로 나뉘며, 서브넷 마스크가 그 경계를 정한다.
  2. 같은 서브넷 안의 기기는 게이트웨이 없이 직접 통신하고, 다른 서브넷이나 인터넷행 패킷은 기본 게이트웨이로 간다.
  3. 10.x, 172.16~31.x, 192.168.x 사설 대역은 외부에서 직접 닿지 않아, 내부 서버를 이용한 SSRF로 내부 시스템에 접근할 수 있다.

용어 해설

서브넷 마스크
IP 주소 중 어디까지가 "같은 동네"이고 어디부터가 "동네 안의 기기 번호"인지 자르는 선이다. /24는 앞의 24비트(앞 세 칸)가 동네 이름이라는 뜻이다.
기본 게이트웨이
내 동네 밖으로 나가는 통신을 대신 전달해 주는 출입문 역할의 장비(보통 공유기)다. 목적지가 다른 동네면 이 장비에 먼저 보낸다.
사설 IP 대역
집·회사 내부에서만 쓰도록 따로 정해둔 주소 범위(192.168.x.x, 10.x.x.x 등)다. 인터넷에는 직접 나가지 않고, 집집마다 같은 주소를 겹쳐 써도 된다.

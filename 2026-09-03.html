P1 · tool_calling_runtime_architecture 공식 changelog FAST-MOVING

Claude Code 헤드리스 모드에 “프롬프트는 자동 거부”라는 새 권한 계층 추가

WHAT

2026-09-02 릴리스된 Claude Code 2.1.259에 --permission-prompts none 플래그가 추가됐다. 공식 changelog 문구는 “anything that would prompt is denied automatically while the active permission mode (including auto mode) keeps deciding”다. 즉 사람이 승인 프롬프트에 답할 수 없는 무인 헤드리스 세션에서, 원래라면 사용자 승인을 요구했을 애매한 권한 판단이 발생하면 자동으로 거부되도록 만드는 옵션이다.

WHY

이 플래그가 다루는 건 도구 화이트리스트(--allowedTools)와는 완전히 다른 층이다. 화이트리스트는 “이 도구를 아예 쓸 수 있는가”를 결정하고, --permission-prompts는 “쓸 수 있는 도구인데 판단이 애매해서 원래는 사람에게 물어봤을 경우를 어떻게 처리할 것인가”를 결정한다. 지금까지는 후자를 다루는 전용 스위치가 없어서, 화이트리스트를 아무리 촘촘히 짜도 그 안에서 발생하는 애매한 경계 케이스가 헤드리스 세션을 무한 대기시킬 위험이 남아 있었다. 활성화된 permission mode(auto mode의 확률적 분류기 포함)는 이 플래그와 무관하게 계속 자기 판단을 내린다 — 이 플래그는 그 판단 체계 밖에서 “그래도 프롬프트가 필요하다고 나온 나머지 경우”만 자동으로 거부 처리하는 별도의 안전장치다.

FOR YOU

이 Knowledge Agent 자체가 지금 GUIDE.md에 문서화된 대로 Windows 작업 스케줄러 + claude -p 헤드리스 실행을 쓰고, tools/run_nightly_brief.ps1이 --allowedTools로 WebSearch/WebFetch/Read/Write/Edit/Agent/Bash(git *)/mcp__kakao-memo__send_kakao_memo만 화이트리스트하는 구조다(agent_harness_engineering.gaps.tool_calling_runtime_architecture, P1, 현재 partial). 지금까지 이 구조에서 “화이트리스트 밖 요청은 거부되지만, 화이트리스트 안인데 판단이 애매한 경우는 어떻게 처리되는지”는 암묵적이었다. --permission-prompts none은 그 두 계층 — 도구 화이트리스트와 프롬프트 처리 정책 — 이 애초에 별개의 축이라는 걸 실제 제품 설계로 보여주는 사례다. 권한 모델을 하나의 온/오프 스위치가 아니라 여러 층으로 나눠 이해해야 한다는, 지금 partial 상태인 바로 그 지점을 정확히 건드린다.

LEARN

claude_code_features는 fast_moving 카테고리라 이 특정 플래그 자체를 깊게 학습할 필요는 없다 — 알아두는 것으로 충분하다. 다만 “permission mode”와 “permission prompts”가 서로 다른 축이라는 개념 프레임은 다른 헤드리스 에이전트(다른 Harness 포함)를 설계할 때도 재사용 가능하므로 개념적으로는 기억해둘 가치가 있다.

  2. 이 플래그는 사람이 승인할 수 없는 상황에서 원래 사용자 승인이 필요했을 애매한 권한 판단을 자동으로 거부 처리한다.
  3. 이는 도구 화이트리스트(--allowedTools)나 활성 permission mode의 판단 체계와는 별개로 작동하는 안전장치다.

용어 해설

P1 · rag_knowledge_systems 공식 발표 EVOLVING PRACTICE

Gemini, 영상을 통째로 넣는 대신 “필요한 구간만 동적으로 찾아가는” 방식으로 전환

WHAT

Google이 Gemini 3.5 Pro 이상 모델에 agentic video understanding을 추가했다고 공식 블로그(blog.google)에서 밝혔다. 기존 방식은 영상을 초당 고정 프레임 수(기본 1fps, API로 조정 가능)로 잘라 전부 context에 넣는 “정적(static)” 처리였다. 새 방식은 모델의 추론 능력과 영상 전용 tool을 결합해, 필요한 구간의 프레임·오디오 트랙·transcript를 그때그때(on demand) 요청하며 영상 타임라인을 동적으로 탐색한다. 공식 발표 기준 긴 영상에서 토큰 사용량을 최대 88%까지 줄이고, 표준 벤치마크에서 분석 비용을 최대 66%, 정확도는 최대 7%까지 개선했다.

WHY

이건 “context를 더 많이 넣을 수 있는가”(context window 크기)와 “context를 더 잘 쓰는가”(활용 품질)가 별개의 축이라는 걸 보여주는 실제 구현 사례다. 고정 fps 프레임 추출은 “일단 다 넣고 모델이 알아서 걸러내라”는 방식이고, agentic navigation은 “필요한 부분만 선택적으로 가져온다”는 방식이다 — 문서 전체를 context에 넣는 대신 관련 chunk만 retrieval하는 RAG와 구조적으로 동일한 패턴을, 텍스트가 아니라 영상이라는 모달리티에 적용한 것이다.

FOR YOU

long_context_reasoning에 이미 기록된 내용과 정확히 맞닿아 있다 — 무한 context window를 가정했을 때 RAG/Sub-agent 필요성이 줄어드는지 스스로 재검토하면서 “Context capacity와 context utilization quality는 별개의 변수일 수 있음”, “RAG는 단순 context 크기 문제만 해결하는 기술이 아님”이라고 이미 결론 내린 바 있다. 이번 Gemini 사례는 그 결론이 실제 프로덕션 모델 설계에 그대로 나타난 것이다 — context window가 충분히 커도(3.5 Pro), “무엇을 언제 가져올지”를 판단하는 별도의 retrieval 계층이 여전히 필요했다. 이는 rag_knowledge_systems의 confirmed_gap인 retrieval/chunking/ranking이 텍스트 RAG에만 국한된 개념이 아니라 “필요한 부분만 선택적으로 가져온다”는 더 일반적인 패턴이라는 걸 보여주는 top-down 연결점이기도 하다.

LEARN

Gemini나 영상 처리를 직접 쓰지 않으므로 이 모델 자체를 깊게 배울 필요는 없다. 다만 “정적 처리 vs 동적/선택적 접근”이라는 패턴은 RAG/context engineering을 설명할 때 재사용 가치가 높다 — AX 강의에서 “RAG가 왜 필요한가”를 설명할 구체적 예시로 쓸 수 있다.

3줄 요약

  1. Google이 Gemini 3.5 Pro 이상 모델에 영상 타임라인을 동적으로 탐색하며 필요한 프레임·오디오·transcript를 그때그때 요청하는 “agentic video understanding”을 추가했다고 공식 블로그에서 밝혔다.
  2. 기존에는 영상을 초당 고정 프레임 수로 추출해 전부 모델에 입력하는 정적 방식을 사용했다.
  3. 공식 발표에 따르면 새 방식은 긴 영상에서 토큰 사용량을 최대 88%, 분석 비용을 최대 66% 줄이면서 정확도는 최대 7% 개선했으며, Interactions API와 GenerateContent API에서 각각 설정을 통해 활성화할 수 있다.

형식 검증 하나가 빠지자 실행까지 뚫렸다 — TLS는 어디에 서 있는가

AI 코딩 에이전트 OpenCode, 웹페이지만 열어도 코드가 실행되는 취약점

WHAT

OpenCode는 AI 코딩 에이전트다. 이 도구의 자동 업그레이드 API가 요청의 형식(Content-Type)을 확인하지 않고 본문을 그대로 JSON으로 해석했다.

공격자는 이 틈을 이용해 브라우저의 요청 차단 규칙(CORS)을 우회하면서도 유효한 JSON 요청을 만들어 보냈다. 그 요청에는 공격자가 지정한 원격 패키지 주소가 업그레이드 대상으로 들어 있었다.

사용자가 악성 웹페이지를 열기만 해도 이 요청이 전송되고, 그 패키지가 설치되는 과정에서 자동 실행 스크립트(preinstall)를 통해 공격자의 코드가 그대로 실행됐다. 클릭도, 승인도 필요 없었다.

WHY

이 취약점은 사용자가 뭔가를 잘못 눌러서 생긴 사고가 아니다. 로컬에서 OpenCode가 돌고 있는 상태로 웹페이지를 열기만 하면 성립한다.

취약했던 82개 릴리스가 조사 기간(2026년 9월 17~23일) 다운로드의 38.9%(64만7천회 이상)를 차지했다. 이건 극소수의 예외적 설정이 아니라, 실제로 널리 깔려 있던 기본 상태였다는 뜻이다.

FOR YOU

당신은 이미 SQL Injection을 볼 때 "위험 문자열을 걸러내는 것"보다 "입력이 쿼리의 구조 자체를 바꿀 수 있는가"를 판단 축으로 쓴다. 이번 사고는 정확히 같은 구조다.

여기서 구조를 바꾼 대상은 SQL문이 아니라 "이 요청을 진짜 JSON으로 처리해도 되는가"라는 판단이었다. Content-Type 확인이 그 판단을 맡는 자리였는데, 그 자리가 비어 있었다.

당신이 도구 실행 경계에서 이미 확인한 "통제 지점은 실제 실행 경로 위에 있어야 한다"는 원칙도 그대로 적용된다. 이번엔 실행 경로 위에 있어야 했던 확인이 "이 본문이 정말 JSON인가"였을 뿐이다.

LEARN

이 CVE 자체를 외울 필요는 없다. 다만 "형식을 검증하지 않으면 그 형식에 실린 것이 곧바로 다음 단계의 신뢰를 넘겨받는다"는 패턴은 API를 설계하거나 검토할 때마다 계속 마주칠 것이다.

3줄 요약

  1. 콘텐츠 타입 검증 누락과 원격 tarball 패키지 허용이 결합해, 방문만으로 실행되는 제로클릭 RCE 취약점이 발생했다.
  2. 영향은 OpenCode 1.14.30~1.18.21이며, 9월 17~23일 다운로드의 38.9%(64만7천회 이상)가 취약 버전이었다.
  3. 2026년 8월 24일 배포된 1.18.22는 업그레이드 패키지를 시맨틱 버전만 허용하고 text/plain 요청에 415를 반환하도록 수정했다.

용어 해설

CORS
웹사이트가 다른 도메인의 서버에 요청을 보낼 때, 브라우저가 "이 요청을 보내도 되는지" 확인하는 보안 규칙이다. 보통은 이 규칙 때문에 악성 페이지가 다른 사이트 서버에 함부로 요청을 못 보낸다.
enctype="text/plain" 제출
웹페이지 입력 양식을 "일반 텍스트로 보낸다"는 설정으로 제출하는 방식이다. CORS 검사를 덜 엄격하게 받기 때문에, 검사를 피해가면서도 서버가 JSON처럼 해석하게 만드는 요청을 몰래 보낼 수 있다.
tarball
여러 파일을 하나로 압축·묶은 배포용 파일이다. 여기서는 공격자가 "이 주소에 있는 파일을 설치 대상으로 써라"라고 지정한 것이다.
preinstall 스크립트
패키지를 설치하는 과정 중 "설치 전"에 자동으로 실행되도록 미리 정해둔 코드다. 사용자가 따로 실행하지 않아도 설치만 되면 자동으로 돌아간다.
zero-click
사용자가 링크를 클릭하거나 뭔가를 입력하는 등 별도 행동을 하지 않아도, 페이지를 열기만 해도 공격이 성립한다는 뜻이다.
시맨틱 버전
"1.18.22"처럼 숫자를 점으로 구분해 표기하는 버전 표기 규칙이다. 패치에서는 업그레이드 대상이 이 정해진 숫자 형식에 맞는지만 확인하도록 검증을 강화했다.

인증서 유무가 아니라, TLS가 어디에 서 있는지

왜 지금 이걸 다루는지

이 주제를 세 번째로 다시 꺼낸다. 8월 27일, 9월 11일, 9월 21일 모두 같은 자리에서 멈췄다 — "TLS는 인증서가 있다 없다는 것"이라는 설명 이상으로 나가지 못했다.

추상적인 계층 설명(아래에서 위로 쌓아 올리는 방식)을 세 번 시도했으니 이번엔 방향을 뒤집는다. 당신이 실제로 겪은 사건에서 거꾸로 올라간다.

당신은 예전에 HTTP/2로 알림을 보내다가, 하드웨어에 저장된 인증서 협상 단계에서 연결이 그대로 멈춘 사건을 겪었다. 연결도 안 되고 에러도 안 뜨는, 이상한 정지 상태였다. 그 멈춘 자리가 바로 TLS다.

무엇을 보장하는가

TLS가 실제로 보장하는 것은 세 가지다. 서버가 진짜 그 서버인지 확인하는 것, 통신 내용을 암호화하는 것, 전송 중 내용이 바뀌면 감지하는 것이다.

"인증서 유무"는 이 중 첫 번째의 일부일 뿐이다. 암호화와 무결성 보호는 인증서와 별개의 축이며, 인증서가 있다고 해서 자동으로 따라오는 것이 아니다.

FOR YOU

당신은 이미 SQL Injection에서 "입력이 구조 자체에 개입할 수 있는가"로 안전/불안전을 가르는 판단 축을 갖고 있다.

TLS도 같은 방식으로 보면 된다. 그 계층에서 정확히 무엇이 검증되고 무엇이 암호화되는지를 나누면, "인증서 유무"라는 하나의 축으로 뭉쳐 있던 것이 서버 인증·암호화·무결성이라는 세 개의 별도 질문으로 풀린다.

LEARN

다음에 이 자리로 돌아올 좋은 기회는, 실제로 당신 시스템이 만드는 HTTPS 연결(카카오 API 호출, GitHub Pages push)의 handshake 로그를 한 번 직접 들여다보는 것이다. 설명으로는 세 번 막혔으니, 다음은 직접 확인이 나을 것이다.

3줄 요약

  1. TLS는 TCP 연결 이후 HTTP 통신 전에 핸드셰이크를 거쳐 암호화 방식 합의, 서버 인증, 키 교환을 수행한다.
  2. TLS가 보장하는 것은 서버 인증, 전송 내용 암호화, 무결성 보호 세 가지이며 인증서 유무는 그중 서버 인증의 일부일 뿐이다.
  3. 핸드셰이크의 클라이언트 인증서 협상 단계에서 하드웨어 보안 모듈 접근과 ALPN 버전 합의가 얽혀 연결이 멈추는 사고가 발생할 수 있다.

용어 해설

PKCS#11
스마트카드나 USB 보안키 같은 하드웨어 장치에 저장된 인증서·키를 프로그램이 표준화된 방식으로 쓸 수 있게 해주는 인터페이스 규격이다.
ALPN
TLS 핸드셰이크 도중 클라이언트와 서버가 이후 HTTP/1.1을 쓸지 HTTP/2를 쓸지 미리 합의하는 확장 기능이다.
